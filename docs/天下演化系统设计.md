# 残明余烬 1.7：天下演化系统设计

## 1. 系统定位

天下演化是主模型背后的世界状态机与旁线叙事台。

- 主模型只负责玩家当前视角内的正文、人物表演与 MVU 更新。
- 天下演化副模型在每轮正文结束后进行一次请求，只提交本轮发生的世界变化和两段旁线场景。
- 脚本保存完整世界档案、校验增量操作、生成下一轮联动包，并在天下演化面板中展示平行世界。
- 平行世界原文不得写回主模型聊天楼层，避免下一轮主模型模仿 `<平行世界>` 标签或旁线文风。

玩家输入只代表行动意图。只有主模型正文、最终 MVU 状态和已经通过天下演化校验的远方变化，才能成为客观事实。

## 2. 设计原则

### 2.1 单次调用

一轮天下演化只调用一次副模型。请求同时返回：

1. 本轮世界状态增量操作；
2. 最多两个可展示的平行世界场景。

不为了核账、推进和写作分别调用多个模型，避免额外等待。

### 2.2 模型只写变化

完整世界档案始终由脚本保存。副模型不得每轮重写整个档案，只返回本轮必要变化。

没有变化的事件、人物、情报和延迟后果不得重复输出。

天下演化不再承担通用记忆职责：世界摘要、近期事实、玩家履历、当前人物状态、地图态势、任务进度和当前时空均由记忆插件、MVU 与状态栏负责。它只补充这些系统通常无法可靠表达的视野外因果。

### 2.3 使用稳定 ID，不使用数组下标

事件、人物、驿报、伏线通过稳定 ID 更新。禁止使用 `/activeEvents/3/stage` 一类依赖数组位置的通用 JSON Patch。

稳定 ID 的所有权属于脚本：

- `upsert` 是语义上的“新增或登记”，模型可以省略 ID；
- 模型把 ID 放在 `actor`、`event`、`intel` 等实体对象内部时，适配层自动提取；
- 新记录没有 ID 时，脚本根据实体类型和稳定身份字段生成 ID；
- 人物 ID 只取人物身份，不把当前位置写入 ID，避免人物移动后被误建成另一人；
- `patch`、`resolve`、`remove` 操作必须引用档案中已经存在的 ID。
- 为兼容供应商偏离 Schema 的输出，`patch` 还携带人物名、事件/伏线标题或情报正文作为身份校验字段；模型给错 ID 时，脚本只在身份唯一匹配时回绑真实 ID。
- 目标确实尚未入档、但误写为 `patch` 且身份与变化内容完整时，脚本将其安全降级为 `upsert`；匿名或身份冲突的 patch 仍然拒绝。

例如：

```json
{
  "type": "event.patch",
  "id": "EVENT-漕粮亏空",
  "set": {
    "stage": "县衙立案",
    "next_trigger": "捕役开始搜查涉案粮铺"
  }
}
```

### 2.4 脚本掌握最终写入权

副模型只能提出操作。脚本负责：

- 把模型语义输出转换为内部操作；
- 在校验前统一剥离 `value`、实体命名对象、字段平铺以及 `attributes`、`properties`、`data`、`payload`、`fields`、`details`、`params`、`arguments` 等常见供应商包装层，并兼容误用于 upsert 的 `set`、`changes`、`patch`；
- 提取或生成新增记录的稳定 ID；
- 只校验模型必须负责的核心语义，不要求模型复述持久化层的全部字段；
- 为精简的事件、人物、情报与伏线补齐内部默认字段；
- 检查目标 ID；
- 合并已有记录；
- 拒绝不完整或越权的操作；
- 按容量限制归档；
- 生成镜头历史；
- 生成下一轮联动包；
- 一次性写入完整新状态。

### 2.5 分区容错

单条非法操作只影响该操作，不使整轮作废。

- 合法操作继续应用；
- 非法操作跳过并记录原因；
- 平行世界缺失不影响合法档案变化；
- 档案中个别操作无效也不影响合法平行世界；
- 顶层结果完全无法解析时才重试整次请求。

被拒绝的操作会在控制台输出类型、ID、外层键和归一化后的载荷键，不记录完整提示词或私密正文。真实接口中出现过的结构必须加入 `scripts/test-world-engine.mjs`，以“整批接受数量”和关键字段映射作为回归断言，避免下次调整协议时再次大面积丢弃。

### 2.6 视野外人物具有自主性

天下档案中的人物不是等待玩家关键词触发的静态条目。只要具备合理的故事时间、行动机会、动机和资源，他们就可以继续原有行动、改变位置、传递消息或作出下一步决策。

- 每轮从当前正文相关人物与轮换队列中选出最多 4 名候选；
- 候选只是检查对象，不要求全部产生变化；
- 副模型每轮最多实际推进 3 名人物，允许 0 人变化；
- 决策必须基于人物的目标、地点、当前行动、已知信息和资源约束；
- `doesNotKnow` 与尚未抵达的情报构成硬知识边界，禁止远距离读心或无渠道同步消息；
- 本轮时间不足时维持原行动，不用无意义 `patch` 假装世界正在推进；
- 人物不必围绕玩家行动，也不必等待玩家进入其所在场景。

## 3. 每轮闭环

1. 主模型收到上一轮压缩后的天下演化联动包。
2. 酒馆完成预设、角色卡、聊天历史、宏、正则和世界书扫描后，脚本从 `CHAT_COMPLETION_PROMPT_READY` / `GENERATE_AFTER_DATA` 捕获主模型当轮实际提示词快照；文本补全源则使用 `GENERATE_AFTER_COMBINE_PROMPTS`。
3. 主模型生成玩家视角正文与 MVU 更新，不生成平行世界。
4. 脚本把提示词快照绑定到 `chatId + messageId + swipeId + messageHash`，只在内存中保留最近少量楼层；聊天切换、消息编辑或删除时清理。
5. 正常情况下，脚本在 MVU `VARIABLE_UPDATE_ENDED` 后开始结算；若未收到事件，使用兜底定时器。
6. 脚本建立视野外人物与活跃事件的轮换工作集，并把“本轮正文 + 轮换工作集”作为最新扫描层，调用酒馆 `getWorldInfoPrompt(..., true)` 做一次定向世界书干扫描；该步骤不请求模型，也不触发世界书激活事件。
7. 脚本以主模型提示词快照为上下文，再追加：
   - 玩家输入，仅作为意图；
   - 当前主模型正文；
   - 最终 MVU 时间、地点与本轮差异；
   - 仍在自行推进的事件、视野外人物行动、在途情报和条件后果工作集；
   - 定向扫描额外命中的世界书条目。
8. 若脚本刷新或中途启用而缺少快照，调用一次酒馆 `dryRun` 重新组装当前提示词；该过程不请求模型。若 dry-run 也不可用，才退回最近聊天兼容上下文。
9. 副模型一次返回 `operations` 和 `parallel_scenes`。
10. 脚本逐条验证操作，在旧状态副本上应用合法变化。
11. 脚本从合法变化生成 `nextTurnPacket`，从旁线场景生成 `cameraHistory`。
12. 脚本再次校验聊天、楼层、重抽页、正文哈希和档案 revision。
13. 校验通过后，一次性保存完整新状态。
14. 平行世界仅进入天下演化档案和 UI，不修改主模型消息。
15. 脚本刷新深度 0 的下一轮主模型联动提示。

提示词快照仍是基础上下文，直接复用主模型当轮真正读取的角色卡、历史、记忆、变量注入和已经激活的世界书。定向扫描只补足两类主模型当轮可能没有命中的内容：正文生成后才出现的关键词，以及轮换到本轮的远方人物、地点、事件和关系。扫描完全使用当前角色、聊天、全局与 Persona 实际绑定的世界书，不读取固定名称；额外条目只交给天下演化副模型，不注入本轮或下一轮主模型，也不自动成为已经发生的事实。

首楼 `messageId = 0` 是开场和初始化内容，不自动推演；只有用户主动点击“重新推演”时才允许处理。

天下演化在后台运行，不得在 `GENERATION_AFTER_COMMANDS`
中长时间阻塞下一轮正文。玩家在结算完成前立即继续时，可以暂时使用上一版联动包；新结果完成后供之后轮次使用。

## 4. 副模型输出协议

```json
{
  "schema_version": 2,
  "base_revision": 17,
  "operations": [
    {
      "type": "actor.upsert",
      "value": {
        "name": "周氏",
        "location": "桐城县·林记米铺后院",
        "goal": "避免旧账落入县衙之手",
        "current_action": "将涉案旧账转交给可信伙计藏匿",
        "knowledge": ["县衙已经开始追查粮铺旧账"],
        "does_not_know": ["玩家尚未掌握旧账的具体藏匿地点"],
        "next_decision": "若捕役抵达便弃铺离城",
        "updated_reason": "本轮玩家行动使搜查压力实际传到米铺"
      }
    },
    {
      "type": "event.patch",
      "id": "EVENT-漕粮亏空",
      "set": {
        "stage": "县衙立案",
        "summary": "缉捕文书已经下发",
        "next_trigger": "捕役开始搜查涉案粮铺"
      }
    }
  ],
  "parallel_scenes": [
    {
      "location": "桐城县·林记米铺后院",
      "time": "酉时",
      "actors": ["周氏"],
      "action": "收起与涉案粮铺有关的旧账",
      "body": "……"
    }
  ]
}
```

`base_revision` 必须等于请求中的档案 revision。脚本不信任模型回传的聊天 ID 或楼层号，而使用请求任务本身绑定的信息。

上例是推荐输出，不是持久化层直接信任的唯一形状。实际写入前必须经过语义适配层：

- `actor.upsert`、`event.upsert`、`intel.upsert`、`hook.upsert` 可使用 `value`，也可使用同名实体对象；
- upsert 记录的 ID 可以位于操作外层、实体内层或完全省略；
- 模型使用 `description/status/source/receiver/arrival_time` 等常见语义字段时，由适配层转换为规范字段；
- 数组形式的 `receivers/recipients/targets` 会合并为情报终点与知情者；
- 新事件只给出内容时，脚本从内容生成短标题，并以当前地点或“地点未明”补齐地点；
- 新情报只需有 `content`，来源、终点、渠道、状态、抵达时间和可靠度缺失时由脚本填入明确的“未明/传播中”默认值；
- 新伏线只需有标题或内容，阶段、触发条件和失效条件由脚本补齐默认值；
- 适配完成后，内部仍统一使用本节定义的规范操作，不把模型原始对象直接写入聊天变量。

这条边界是稳定性的核心：模型负责“世界发生了什么”，脚本负责“档案怎样存”。持久化层字段不得反向成为副模型输出的脆弱前置条件。

## 5. 增量操作

### 5.1 事件

- `event.upsert`：创建新的持续事件。模型至少提供标题、摘要或内容之一；阶段、地点和下一触发条件缺失时由脚本补齐。
- `event.patch`：只提交已有事件发生变化的字段。
- `event.resolve`：结束事件并从活跃事件中移除。

`event.patch` 的 `id` 不存在且载荷没有可唯一核对的事件标题时拒绝，不自动创建匿名空事件。

### 5.2 人物

- `actor.upsert`：创建确有当前行动的重要人物。
- `actor.patch`：更新已有角色的位置、目标、当前行动、`knowledge`、`does_not_know`、下一决策或更新原因。

不得仅因人物出现在角色资料、名册、状态栏或当前在场人物变量中就建档；只有其视野外行动、知识或下一决策发生变化时才进入天下档案。

已建档人物会进入轮换检查。人物可以在玩家视角外继续做自己的事，但一次推进必须满足时间、距离、资源和知识条件；若没有新结果，保持现有记录即可。

### 5.3 情报

- `intel.upsert`：创建在途信息包。模型至少提供情报内容；传播元数据不足时脚本以“来源未明、去向未明、口耳相传、传播中、抵达时间未明”保存，而不是丢弃整条情报。
- `intel.patch`：更新传播位置、状态、预计抵达时间和知情者。
- `intel.remove`：情报失效、被截获或已经完成传播后移除。

静态秘密和人物心意不属于在途情报。

### 5.4 条件后果

- `hook.upsert`：创建等待条件兑现的因果债。模型至少提供标题或内容，并应说明触发条件和失效条件。
- `hook.patch`：推进阶段、征兆或条件。
- `hook.resolve`：伏线已经触发、失效或不再需要追踪。

## 6. 脚本派生字段

以下字段不由副模型重复输出。

### 6.1 `cameraHistory`

从 `parallel_scenes` 的地点、人物和行动生成，保留最近若干条，用于防止连续重复镜头。

### 6.2 `nextTurnPacket`

由脚本根据本轮合法操作生成：

- `offscreenMoves`：玩家视野外人物正在执行的行动与下一决策；
- `arrivingIntel`：已经进入玩家可知范围的情报；
- `intelInTransit`：仍在传播、尚不可直接得知的消息及传播路径；
- `npcKnowledge`：本轮人物知识变化；
- `activePressures`：本轮推进的活跃事件；
- `pendingConsequences`：等待触发条件兑现的因果债；
- `uncertainties`：可靠度不足、彼此冲突或尚未证实的信息；
- `constraints`：固定知识边界与本轮不得提前泄露的内容。

下一轮主模型不会收到平行世界原文。

## 7. 平行世界

### 7.1 内容要求

- 每轮最多两个玩家视野之外的场景；
- 每段包含地点、时点、人物、行动和正文；
- 优先展示本轮实际推进的事件、人物行动或情报传播；
- 素材不足时可以写低风险日常切片；
- 不得重演玩家当前场景；
- 不得凭空制造重大胜负、死亡、陷城和政局结果；
- 不使用 `<平行世界>` 标签和元叙事转场。

### 7.2 保存与展示

平行世界按回合保存在聊天级天下档案中，记录：

- 来源楼层和重抽页；
- 生成时间；
- 档案 revision；
- 最多两个场景；
- 本轮接受与拒绝的操作数量。

面板提供独立“旁线”栏目。重新推演同一楼层时替换该楼层原有旁线，不重复追加。

旧聊天楼层中已经存在的 `<平行世界>` 保持原样，不主动修改；新版本不再写入新的标签块。

## 8. 工作集与职责去重

每轮不向副模型发送全部档案，而发送相关工作集：

- 当前正文命中的活跃事件；
- 当前涉及或正在进行视野外行动的重要人物；
- 按档案 revision 轮换到本轮的远方人物与事件，避免长期未被正文提及的对象永远停滞；
- 临近抵达或命中相关地区的情报；
- 可能被本轮条件触发的因果债。

主模型当轮提示词快照已经包含角色卡、世界书、聊天历史、记忆插件摘要和 MVU 注入，因此天下演化不再额外构造人物、势力、地图、当前时空和近期事实概要。旧版聊天变量中的 `worldSummary` 与 `facts` 读取后会清空，不再进入请求、联动提示或 UI。

工作集还用于定向世界书扫描。扫描文本的第 0 层包含当前正文、候选人物的姓名/地点/目标/行动/知识边界，以及候选事件的标题/地点/参与者/下一触发条件。这样世界书扫描深度即使只有 1，也能命中对应条目。脚本使用酒馆原生扫描器及当前实际绑定关系，不硬编码任何世界书名称；同主提示词快照重复的完整条目会跳过。

默认上限：

- 活跃事件 24 条；
- 重要人物 48 名；
- 在途情报 60 条；
- 活跃伏线 16 条；
- 镜头历史 18 条；
- 平行世界回合 24 轮；
- 检查点 8 个。

## 9. 一致性与并发

每个任务绑定：

```text
chatId + messageId + swipeId + messageHash + baseRevision
```

写入前再次比较。任一字段变化，返回结果视为过期并丢弃。

- 同一时刻只执行一个天下演化请求；
- 新任务到来时只保留最新待处理任务；
- 切换聊天时停止旧请求、清空定时器和待处理任务；
- 重抽或编辑从目标楼层之前的检查点恢复；
- 删除楼层后恢复到最近有效检查点；
- 保存前先在内存副本中应用全部合法操作，不边解析边写变量。

## 10. 请求与失败策略

- 默认温度：`1`；
- 默认最大输出：`10000`；
- 独立 API 与当前酒馆连接均应尽可能使用同一组模型参数；
- 请求超时后主动停止对应 generation ID；
- 顶层 JSON 或结构完全无法解析时最多自动重试一次；
- 用户主动停止后不重试；
- 单条操作失败不重试整个请求；
- upsert 缺少 ID 不视为失败，由脚本生成；只有修改或结束旧记录时缺少 ID 才拒绝；
- 已有记录在旧版本中缺失 ID 时，读取档案即根据稳定身份字段补齐；
- patch 的 ID 错误但身份字段唯一命中旧记录时，本地回绑，不增加副模型调用；
- upsert 缺少内部存档元数据不视为失败；只有事件、情报或伏线连核心语义内容也为空时才拒绝；
- UI 显示错误分类、最后成功楼层、接受操作数和拒绝操作数。

错误分为：

1. 连接或请求错误；
2. 顶层解析错误；
3. 操作校验错误；
4. 过期结果；
5. 保存错误。

## 11. 设置迁移

设置版本由 2 升级为 3。

- 未保存温度或仍使用旧默认 `0.45` 的用户迁移到 `1`；
