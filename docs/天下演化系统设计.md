# 残明余烬 1.7：天下演化系统设计

## 1. 系统定位

天下演化是主模型背后的世界状态机与旁线叙事台。

- 主模型只负责玩家当前视角内的正文、人物表演与 MVU 更新。
- 天下演化副模型在每轮正文结束后进行一次请求，只提交本轮发生的世界变化和两段旁线场景。
- 脚本保存完整世界档案、校验增量操作、生成下一轮联动包，并在天下演化面板中展示平行世界。
- 平行世界原文不得写回主模型聊天楼层，避免下一轮主模型模仿 `<平行世界>` 标签或旁线文风。

玩家输入只代表行动意图。只有主模型正文、最终 MVU 状态和已经通过天下演化校验的远方变化，才能成为客观事实。

## 2. 设计原则

### 2.1 单次调用

一轮天下演化只调用一次副模型。请求同时返回：

1. 本轮世界状态增量操作；
2. 最多两个可展示的平行世界场景。

不为了核账、推进和写作分别调用多个模型，避免额外等待。

### 2.2 模型只写变化

完整世界档案始终由脚本保存。副模型不得每轮重写整个档案，只返回本轮必要变化。

没有变化的事件、人物、情报和延迟后果不得重复输出。

天下演化不再承担通用记忆职责：世界摘要、近期事实、玩家履历、当前人物状态、地图态势、任务进度和当前时空均由记忆插件、MVU 与状态栏负责。它只补充这些系统通常无法可靠表达的视野外因果。

### 2.3 使用稳定 ID，不使用数组下标

事件、人物、驿报、伏线通过稳定 ID 更新。禁止使用 `/activeEvents/3/stage` 一类依赖数组位置的通用 JSON Patch。

稳定 ID 的所有权属于脚本：

- `upsert` 是语义上的“新增或登记”，模型可以省略 ID；
- 模型把 ID 放在 `actor`、`event`、`intel` 等实体对象内部时，适配层自动提取；
- 新记录没有 ID 时，脚本根据实体类型和稳定身份字段生成 ID；
- 人物 ID 只取人物身份，不把当前位置写入 ID，避免人物移动后被误建成另一人；
- `patch`、`resolve`、`remove` 操作必须引用档案中已经存在的 ID。
- 为兼容供应商偏离 Schema 的输出，`patch`
  还携带人物名、事件/伏线标题或情报正文作为身份校验字段；模型给错 ID 时，脚本只在身份唯一匹配时回绑真实 ID。
- 目标确实尚未入档、但误写为 `patch` 且身份与变化内容完整时，脚本将其安全降级为
  `upsert`；匿名或身份冲突的 patch 仍然拒绝。

例如：

```json
{
  "type": "event.patch",
  "id": "EVENT-漕粮亏空",
  "set": {
    "stage": "县衙立案",
    "next_trigger": "捕役开始搜查涉案粮铺"
  }
}
```

### 2.4 脚本掌握最终写入权

副模型只能提出操作。脚本负责：

- 把模型语义输出转换为内部操作；
- 在校验前统一剥离 `value`、实体命名对象、字段平铺以及
  `attributes`、`properties`、`data`、`payload`、`fields`、`details`、`params`、`arguments`
  等常见供应商包装层，并兼容误用于 upsert 的 `set`、`changes`、`patch`；
- 提取或生成新增记录的稳定 ID；
- 只校验模型必须负责的核心语义，不要求模型复述持久化层的全部字段；
- 为精简的事件、人物、情报与伏线补齐内部默认字段；
- 检查目标 ID；
- 合并已有记录；
- 拒绝不完整或越权的操作；
- 按容量限制归档；
- 生成镜头历史；
- 生成下一轮联动包；
- 一次性写入完整新状态。

### 2.5 分区容错

单条非法操作只影响该操作，不使整轮作废。

- 合法操作继续应用；
- 非法操作跳过并记录原因；
- 平行世界缺失不影响合法档案变化；
- 档案中个别操作无效也不影响合法平行世界；
- 顶层结果完全无法解析时才重试整次请求。

被拒绝的操作会在控制台输出类型、ID、外层键和归一化后的载荷键，不记录完整提示词或私密正文。真实接口中出现过的结构必须加入
`scripts/test-world-engine.mjs`，以“整批接受数量”和关键字段映射作为回归断言，避免下次调整协议时再次大面积丢弃。

### 2.6 视野外人物具有自主性

天下档案中的人物不是等待玩家关键词触发的静态条目。只要具备合理的故事时间、行动机会、动机和资源，他们就可以继续原有行动、改变位置、传递消息或作出下一步决策。

- 每轮从当前正文相关人物与轮换队列中选出最多 4 名候选；
- 候选只是检查对象，不要求全部产生变化；
- 副模型每轮最多实际推进 3 名人物，允许 0 人变化；
- 决策必须基于人物的目标、地点、当前行动、已知信息和资源约束；
- `known / suspected / believed` 分别表示已知、怀疑和主观相信，三者不得混用；
- `doesNotKnow`、未获白名单授权的秘密与尚未抵达的情报构成硬知识边界，禁止远距离读心或无渠道同步消息；
- 本轮时间不足时维持原行动，不用无意义 `patch` 假装世界正在推进；
- 人物不必围绕玩家行动，也不必等待玩家进入其所在场景。

### 2.7 信息默认拒绝，而不是默认共享

酒馆会把世界书、变量、状态栏和记忆一并交给模型，但“模型看见”不等于“人物知道”。天下演化额外维护两层权限：

1. 人物知识账本：按人物记录 `known`、`suspected`、`believed`、来源、来源实体、置信度和取得时间；
2. 秘密登记簿：记录秘密正文、保密等级、合法知情者白名单、允许揭露条件、状态和证据来源。

主模型每轮生成前，脚本根据最近聊天和联动包选出最多 6 名相关人物，注入完整的权限卡：

- 可以当作事实使用的已知内容；
- 只能用于试探的怀疑；
- 可以驱动行动、但不能当成真相播报的主观相信；
- 完整的 `doesNotKnow` 硬盲区；
- 获准持有的秘密。

隐藏或已经泄露但尚未公开的秘密登记簿会作为“系统真相”整体注入，并明确规定知情者是白名单：未列名人物一律不知道。未选入权限卡的人物也执行默认拒绝，不能因为世界书或旁白出现了某项事实便自动获得知识。

知识边界只能通过带来源的 `knowledge.*` 或 `secret.reveal` 改变。校验由脚本本地完成，不会为了“再检查一次”额外请求模型。

### 2.8 本轮事实先分配可见范围

只隐藏玩家原始输入不能解决全知，因为玩家行动的结果还会出现在主模型正文中。系统因此不再把整段 `CURRENT_TURN`
当作所有人物都能引用的知识来源，而是在同一次天下演化响应中先建立 `turn_facts`：

- `private`：无人目击，目击者强制为空；
- `addressed`：只对明确被告知或被展示的人可见；
- `scene_visible`：只对本地核实在场并在正文中实际出现的人可见；
- `local_public`：当前地点内的公开表现，但仍只授予已经核实的本地目击者，不会瞬间扩散到全城或远方。

每项事实必须附带主模型正文中的逐字证据、客观物理结果、可发现痕迹和发现条件。若副模型把证据改写成近义句，但事实内容仍能在正文中定位，脚本会从正文中回收对应原句再保存；无法定位时仍拒绝该事实，不能用语义猜测放宽证据边界。脚本结合最终 MVU中的“是否在场”、当前地点、正文实际出现的人名和上一轮同地点在场缓存，生成可靠目击者集合；副模型提交的目击者只能取其交集。无法核实的目击者会被移除，没有任何合法目击者时事实降级为
`private`。

无人目击的事实仍会改变客观世界并写入聊天级天下档案，但不会自动写进任何人物知识。以后 NPC 只能通过 `trace.discover`
在实际场景或事件中发现已登记痕迹，并且只获得痕迹能支持的有限结论，例如“石缝最近被动过”，不能直接推出“玩家把密信藏在这里”。

人物行动、事件参与者、情报起点、知识操作和旁线场景都会再次引用这层事实权限进行本地校验。因此即使副模型已经读到完整正文，也不能让未目击 NPC 立即反应。

## 3. 每轮闭环

1. 主模型收到上一轮压缩后的天下演化联动包：本轮新近变化优先，并补充少量仍未结束的核心状态。
2. 酒馆完成预设、角色卡、聊天历史、宏、正则和世界书扫描后，脚本从 `CHAT_COMPLETION_PROMPT_READY` / `GENERATE_AFTER_DATA`
   捕获主模型当轮实际提示词快照；文本补全源则使用 `GENERATE_AFTER_COMBINE_PROMPTS`。
3. 主模型生成玩家视角正文与 MVU 更新，不生成平行世界。
4. 脚本把提示词快照绑定到
   `chatId + messageId + swipeId + messageHash`，只在内存中保留最近少量楼层；聊天切换、消息编辑或删除时清理。
5. 正常情况下，脚本在 MVU `VARIABLE_UPDATE_ENDED` 后开始结算；若未收到事件，使用兜底定时器。
6. 脚本从剔除状态栏、`initvar`
   和旧平行世界后的纯正文核实本轮实际出场者，再结合 MVU 在场状态建立目击许可；同时建立视野外人物与活跃事件的轮换工作集，并把“本轮正文 + 轮换工作集”作为最新扫描层，调用酒馆
   `getWorldInfoPrompt(..., true)` 做一次定向世界书干扫描；该步骤不请求模型，也不触发世界书激活事件。
7. 脚本以主模型提示词快照为上下文，再追加：
   - 玩家输入，仅作为意图；
   - 当前主模型正文；
   - 最终 MVU 时间、地点与本轮差异；
   - 仍在自行推进的事件、视野外人物行动、在途情报和条件后果工作集；
   - 本轮生成许可
     `GENERATION_LICENSE`：合法目击者、各类可修改记录 ID、逐人物可用的观察/知识/已抵达情报/参与事件 ID，以及安全的自主行动候选；
   - 定向扫描额外命中的世界书条目。
8. 若脚本刷新或中途启用而缺少快照，调用一次酒馆 `dryRun`
   重新组装当前提示词；该过程不请求模型。若 dry-run 也不可用，才退回最近聊天兼容上下文。
9. 副模型先按生成许可构造候选变化，并在同一次输出前静默检查 ID 类型、人物知识权限与旁线事实引用；随后一次返回
   `turn_facts`、`operations` 和 `parallel_scenes`，不增加第二次校验调用。
10. 脚本仍以确定性规则核对事实证据、可靠目击者和知识传播链，但它是防止模型偶发越权的最后保险，不承担正常生成的主要纠错职责；无传播链的变化只拒绝该项。
11. 脚本在旧状态副本上应用合法变化：本轮事实与痕迹、人物行动、知识账本、秘密登记簿和可靠在场缓存分别合并，`actor.patch`
    不能夹带知识。
12. 脚本从合法变化生成
    `nextTurnPacket`，再从完整档案中选出最近更新且仍未结束的核心事件、人物行动、伏线和在途情报，组成下一轮双层联动包；旁线场景只生成
    `cameraHistory`。
13. 脚本再次校验聊天、楼层、重抽页、正文哈希和档案 revision。
14. 校验通过后，一次性保存完整新状态。
15. 平行世界仅进入天下演化档案和 UI，不修改主模型消息。
16. 脚本刷新深度 0 的下一轮主模型联动提示；下一次 `GENERATION_STARTED`
    时再按最新玩家输入动态刷新相关人物权限卡，不调用模型。

提示词快照仍是基础上下文，直接复用主模型当轮真正读取的角色卡、历史、记忆、变量注入和已经激活的世界书。定向扫描只补足两类主模型当轮可能没有命中的内容：正文生成后才出现的关键词，以及轮换到本轮的远方人物、地点、事件和关系。扫描完全使用当前角色、聊天、全局与 Persona 实际绑定的世界书，不读取固定名称；额外条目只交给天下演化副模型，不注入本轮或下一轮主模型，也不自动成为已经发生的事实。

“复用主模型提示词快照”指复用同一来源和实际激活结果，不代表把主请求逐字复制一遍。发送前脚本会做确定性的预算化整理：

- 只投影档案中结算需要的字段，并限制单个人物的知识账本、事实和记录数量；
- 当前正文、玩家意图、兼容聊天上下文均按头尾保留，避免超长楼层占满请求；
- 主提示词快照最多保留 9000 字符，定向世界书最多保留 7000 字符，完整请求提示词硬上限约 42000 字符；
- JSON Schema 以紧凑 JSON 写入提示词，不向代理发送原生 `json_schema`；
- 设置中的输出长度仍表示用户期望上限；单次请求会按输入规模动态取较小值，且不超过 8000
  tokens，避免输入与输出预算之和超过代理或模型限制。

预算化过程不调用模型，也不生成概要；当前正文、定向世界书、因果工作集和输出规则优先保留。控制台只打印提示词字符数与实际输出上限，接口返回
`Bad Request` 时面板也会显示这组诊断数据。

### 3.1 生成许可

天下演化采用“生成前白名单，生成后硬兜底”的结构。`GENERATION_LICENSE` 由脚本确定性生成，主要包含：

- `witnessPolicy.allowedNames`：可以写入本轮 `turn_facts.witnesses`
  的姓名；正文明确出场者即使 MVU 的“是否在场”尚未更新，也可以进入该名单；
- `witnessPolicy.forbiddenKnownNames`：世界书、旧档案或状态栏中已知，但本轮没有可靠在场证据的人物；
- `patchTargets`：人物、事件、情报、伏线和秘密可以直接复用的稳定 ID；不在名单中的目标只能 `upsert`；
- `safeAutonomyCandidates`：逐人物列出可用于行动的旧观察、知识账目、已抵达情报和参与事件 ID，禁止跨类型引用；
- `newNarrativeActorCandidates`：正文明确出场但尚未进入天下档案的人物，只能使用 `actor.upsert`；
- `silentPreflight`：要求副模型在输出前自行删除 ID 不存在、因果类型错配、知识越权或无法证明的旁线。

正文出场识别只扫描 `stripForContext` 后的叙事文本，避免人物仅在 `<initvar>`
或状态栏资料中出现就被误判为目击者。若没有安全的既有人物可以推进，模型可以从只读上下文新建一名视野外人物，但必须使用
`elapsed_time / ELAPSED_TIME`，不得引用当前回合事实；无法与当前回合脱钩时应返回空旁线。

首楼 `messageId = 0` 是开场和初始化内容，不自动推演；只有用户主动点击“重新推演”时才允许处理。

天下演化在后台运行，不得在 `GENERATION_AFTER_COMMANDS`
中长时间阻塞下一轮正文。玩家在结算完成前立即继续时，可以暂时使用上一版联动包；新结果完成后供之后轮次使用。

上例是推荐输出，不是持久化层直接信任的唯一形状。实际写入前必须经过语义适配层：

- `actor.upsert`、`event.upsert`、`intel.upsert`、`hook.upsert` 可使用 `value`，也可使用同名实体对象；
- upsert 记录的 ID 可以位于操作外层、实体内层或完全省略；
- 模型使用 `description/status/source/receiver/arrival_time` 等常见语义字段时，由适配层转换为规范字段；
- 数组形式的 `receivers/recipients/targets` 会合并为情报终点与知情者；
- 新事件只给出内容时，脚本从内容生成短标题，并以当前地点或“地点未明”补齐地点；
- 新情报只需有 `content`，来源、终点、渠道、状态、抵达时间和可靠度缺失时由脚本填入明确的“未明/传播中”默认值；
- 新伏线只需有标题或内容，阶段、触发条件和失效条件由脚本补齐默认值；
- 适配完成后，内部仍统一使用本节定义的规范操作，不把模型原始对象直接写入聊天变量。

这条边界是稳定性的核心：模型负责“世界发生了什么”，脚本负责“档案怎样存”。持久化层字段不得反向成为副模型输出的脆弱前置条件。

## 5. 增量操作

### 5.1 事件

- `event.upsert`：创建新的持续事件。模型至少提供标题、摘要或内容之一；阶段、地点和下一触发条件缺失时由脚本补齐。
- `event.patch`：只提交已有事件发生变化的字段。
- `event.resolve`：结束事件并从活跃事件中移除。

`event.patch` 的 `id` 不存在且载荷没有可唯一核对的事件标题时拒绝，不自动创建匿名空事件。

### 5.2 人物

- `actor.upsert`：创建确有当前行动的重要人物。
- `actor.patch`：只更新已有角色的位置、目标、当前行动、下一决策或更新原因。

不得仅因人物出现在角色资料、名册、状态栏或当前在场人物变量中就建档；只有其视野外行动、知识或下一决策发生变化时才进入天下档案。

已建档人物会进入轮换检查。人物可以在玩家视角外继续做自己的事，但一次推进必须满足时间、距离、资源和知识条件；若没有新结果，保持现有记录即可。

人物变化使用 `cause_type / cause_id / basis_ids`
说明因果依据。允许的原因包括自主行动、时间流逝、合法目击、已有知识、已抵达情报和参与事件。人物行动若与本轮事实有关，必须引用该人物有权目击的
`TF-*`；与本轮正文直接相关却没有来源的远方反应会被拒绝。为减少模型字段顺序造成的偶发错误，脚本先处理事件和情报，再处理人物行动，最后处理知识与痕迹发现。

已有角色的 `knowledge` 与 `does_not_know` 不再允许通过 `actor.patch`
改写。兼容层仍会保留旧角色记录中的这两个字段，但新的认知变化必须走下述知识操作；即使模型把知识夹带在人物 patch 中，脚本也会恢复旧值。

### 5.3 情报

- `intel.upsert`：创建在途信息包。模型至少提供情报内容；传播元数据不足时脚本以“来源未明、去向未明、口耳相传、传播中、抵达时间未明”保存，而不是丢弃整条情报。
- `intel.patch`：更新传播位置、状态、预计抵达时间和知情者。
- `intel.remove`：情报失效、被截获或已经完成传播后移除。

静态秘密和人物心意不属于在途情报。

情报若复述本轮事实，必须在 `source_fact_ids` 中引用对应 `TF-*`，并且情报起点必须是该事实的合法目击者。模型写错本地
`TF-*` 别名时，脚本会根据已经通过校验且与记录内容相关的本轮事实重绑稳定 ID，不因纯引用错误丢弃整条记录。`local_public`
事实可以从“西街邻里传闻、坊间议论、官府告示”等现场公共渠道开始传播；`private`、`addressed` 和普通 `scene_visible`
事实仍必须从明确的合法知情者出发。无人目击事实不能直接生成“全城已经传开”的情报。

### 5.4 条件后果

- `hook.upsert`：创建等待条件兑现的因果债。模型至少提供标题或内容，并应说明触发条件和失效条件。
- `hook.patch`：推进阶段、征兆或条件。
- `hook.resolve`：伏线已经触发、失效或不再需要追踪。

### 5.5 知识权限与秘密

- `knowledge.grant`：人物已经通过可靠渠道得知某项事实；
- `knowledge.suspect`：人物只有迹象，允许怀疑和试探，不得当作真相；
- `knowledge.mislead`：人物主观相信某项信息，但它可能是错误的；
- `knowledge.correct`：以新证据纠正旧认知，可用 `replaces` 指明被替换内容；
- `secret.upsert`：登记需要防全知的重要秘密及其知情者白名单；
- `secret.patch`：更新已有秘密的状态、知情者或揭露条件；
- `secret.reveal`：通过一次可核验传播，把指定秘密授予某个人物；
- `trace.discover`：人物在后续场景或事件中发现既有事实留下的痕迹，只登记痕迹支持的有限结论。

每项知识操作至少包含人物、内容、`source_type`、`source_id` 和 `confidence`。支持的来源：

| `source_type`        | 本地校验                                                                   |
| -------------------- | -------------------------------------------------------------------------- |
| `direct_observation` | 人物是 `TF-*` 的合法目击者，或在事件、旁线场景中实际观察到对应内容         |
| `witnessed_event`    | 事件存在、人物列在参与者中，内容与事件相符                                 |
| `received_intel`     | 情报存在、已经抵达、人物是接收者，内容相符；确定知识还要求可靠度不低于 0.6 |
| `told_by_actor`      | 告知者自己已知，并且本轮正文或共同在场事件能证明双方实际发生了告知         |
| `public_information` | 情报已经公开抵达；本轮事实还要求 `local_public` 且人物在合法目击者名单中   |
| `correction`         | 存在已抵达情报、事件或本轮在场纠正作为证据                                 |

`told_by_actor` 另填 `source_actor_id / source_actor_name` 指明告知者，`source_id` 必须是发生告知的
`TF-*`、`PARALLEL_SCENE_N` 或双方共同在场的事件 ID，不能拿告知者 ID 冒充传播渠道。引用本次返回的第 N 段旁线时统一使用
`PARALLEL_SCENE_N`，不存在的编号不能通过校验。

`CURRENT_TURN` 不再是可直接授予知识或登记秘密的来源。主模型正文中的结果必须先成为通过证据与目击者校验的
`TF-*`，之后知识、秘密、事件、情报、人物行动和旁线才能引用它。无来源、来源不存在、消息仍在途中、告知者自己不知道、双方没有实际接触、人物不在现场等情况都会被逐项拒绝。

新建秘密时，知情者也必须出现在同一份证据中：本轮正文要实际出现该人物，事件来源要把人物列为参与者，情报来源则必须已经抵达该接收者。后续增加知情者只能使用
`secret.reveal`；`secret.patch` 不能夹带新的白名单成员。

这些检查都是字符串、实体关系和状态判断，不进行额外模型调用。只有原本的一次天下演化请求；顶层 JSON 完全损坏时的兼容重试属于请求失败策略，不是知识校验步骤。

## 6. 脚本派生字段

以下字段不由副模型重复输出。

### 6.1 `cameraHistory`

从 `parallel_scenes` 的地点、人物和行动生成，保留最近若干条，用于防止连续重复镜头。

### 6.2 `nextTurnPacket`

第一层由脚本根据本轮合法操作生成：

- `offscreenMoves`：玩家视野外人物正在执行的行动与下一决策；
- `arrivingIntel`：已经进入玩家可知范围的情报；
- `intelInTransit`：仍在传播、尚不可直接得知的消息及传播路径；
- `npcKnowledge`：本轮人物知识变化；
- `activePressures`：本轮推进的活跃事件；
- `pendingConsequences`：等待触发条件兑现的因果债；
- `uncertainties`：可靠度不足、彼此冲突或尚未证实的信息；
- `constraints`：固定知识边界与本轮不得提前泄露的内容。

第二层由脚本从完整档案中按最近更新时间补充少量仍未结束的核心状态：

- 最近仍在行动、但本轮没有发生变化的视野外人物；
- 仍在施压的活跃事件；
- 尚未兑现或失效的伏线；
- 尚未抵达的在途情报；
- 仍然有效的人物知识边界与低可靠度信息。

两层按人物姓名、事件标题或摘要、伏线标题或摘要、情报正文去重。本轮变化优先；持续状态只作为因果与知识约束，不要求主模型强行播报或切换镜头。每类本轮变化最多注入 8 条、持续状态最多 4 条，单条最多 240 字。

`nextTurnPacket.npcKnowledge`
只负责标记本轮哪些人物的知识发生过变化。真正给主模型使用的知识内容不再从这个压缩字段截取，而是在每次正文生成前从完整持久账本重新生成权限卡，避免关键盲区因压缩而丢失。

下一轮主模型不会收到完整事件/情报/伏线档案、已经解决的项目或平行世界原文。它会收到：

- 最多 6 名当前相关人物的完整知识权限卡；
- 所有仍处于 `hidden / compromised` 的秘密登记项；
- 明确的默认拒绝和秘密白名单协议。

每名人物最多注入 12 条已知事实、8 条怀疑、8 条主观相信；`doesNotKnow`
使用人物档案内完整列表，不再只截取三条。人物知识单条最多 160 字，秘密正文单条最多 300 字。

## 7. 平行世界

### 7.1 内容要求

- 每轮最多两个玩家视野之外的场景；
- 每段包含地点、时点、人物、行动和正文；
- 优先展示本轮实际推进的事件、人物行动或情报传播；
- 素材不足时可以写低风险日常切片；
- 不得重演玩家当前场景；
- 不得凭空制造重大胜负、死亡、陷城和政局结果；
- 不使用 `<平行世界>` 标签和元叙事转场。

### 7.2 保存与展示

平行世界按回合保存在聊天级天下档案中，记录：

- 来源楼层和重抽页；
- 生成时间；
- 档案 revision；
- 最多两个场景；
- 本轮接受与拒绝的操作数量。

面板提供独立“旁线”栏目。重新推演同一楼层时替换该楼层原有旁线，不重复追加。

旧聊天楼层中已经存在的 `<平行世界>` 保持原样，不主动修改；新版本不再写入新的标签块。

## 8. 工作集与职责去重

每轮不向副模型发送全部档案，而发送相关工作集：

- 当前正文命中的活跃事件；
- 当前涉及或正在进行视野外行动的重要人物；
- 按档案 revision 轮换到本轮的远方人物与事件，避免长期未被正文提及的对象永远停滞；
- 临近抵达或命中相关地区的情报；
- 可能被本轮条件触发的因果债。

主模型当轮提示词快照已经包含角色卡、世界书、聊天历史、记忆插件摘要和 MVU 注入，因此天下演化不再额外构造人物、势力、地图、当前时空和近期事实概要。旧版聊天变量中的
`worldSummary` 与 `facts` 读取后会清空，不再进入请求、联动提示或 UI。

工作集还用于定向世界书扫描。扫描文本的第 0 层包含当前正文、候选人物的姓名/地点/目标/行动/知识边界，以及候选事件的标题/地点/参与者/下一触发条件。这样世界书扫描深度即使只有 1，也能命中对应条目。脚本使用酒馆原生扫描器及当前实际绑定关系，不硬编码任何世界书名称；同主提示词快照重复的完整条目会跳过。

默认上限：

- 活跃事件 24 条；
- 重要人物 48 名；
- 每名人物知识账本 40 条；
- 在途情报 60 条；
- 活跃伏线 16 条；
- 秘密登记簿 24 条；
- 镜头历史 18 条；
- 平行世界回合 24 轮；
- 检查点 8 个。

## 9. 一致性与并发

每个任务绑定：

```text
chatId + messageId + swipeId + messageHash + baseRevision
```

写入前再次比较。任一字段变化，返回结果视为过期并丢弃。

- 同一时刻只执行一个天下演化请求；
- 新任务到来时只保留最新待处理任务；
- 切换聊天时停止旧请求、清空定时器和待处理任务；
- 重抽或编辑从目标楼层之前的检查点恢复；
- 删除楼层后恢复到最近有效检查点；
- 保存前先在内存副本中应用全部合法操作，不边解析边写变量。

## 10. 请求与失败策略

- 默认温度：`1`；
- 默认最大输出：`10000`；
- 默认请求超时：`90` 秒，可在设置中调整为 `30—900` 秒；
- 独立 API 与当前酒馆连接均应尽可能使用同一组模型参数；
- 所有模型和连接默认使用“提示词 Schema”：结构定义随提示词发送，不向代理提交原生 `json_schema / response_format`；
- 不根据模型名或 API 地址猜测原生结构化输出能力，避免 DeepSeek、Gemini、Claude 及第三方 OpenAI 兼容代理被错误分流；
- 正常成功仍只有一次副模型调用；只有返回内容无法解析时才允许一次格式修复重试；
- 请求超时后主动停止对应 generation ID；
- 推演开始后在酒馆主界面显示横幅；横幅中的“取消”会立刻终止对应 generation ID，并清空尚未开始的排队任务；
- 推演完成和主动取消的横幅自动收起，失败横幅保留到用户关闭，避免错误被一闪而过；
- 顶层 JSON 或结构完全无法解析时最多自动重试一次；连接错误、超时和用户取消不重试；
- 用户主动停止后不重试；
- 单条操作失败不重试整个请求；
- upsert 缺少 ID 不视为失败，由脚本生成；只有修改或结束旧记录时缺少 ID 才拒绝；
- 已有记录在旧版本中缺失 ID 时，读取档案即根据稳定身份字段补齐；
- patch 的 ID 错误但身份字段唯一命中旧记录时，本地回绑，不增加副模型调用；
- upsert 缺少内部存档元数据不视为失败；只有事件、情报或伏线连核心语义内容也为空时才拒绝；
- 知识来源、秘密来源和秘密揭露链全部本地校验，失败只忽略对应操作，不追加模型调用；
- UI 显示错误分类、最后成功楼层、接受操作数和拒绝操作数。

错误分为：

1. 连接或请求错误；
2. 顶层解析错误；
3. 操作校验错误；
4. 过期结果；
5. 保存错误。

## 11. 设置迁移

设置版本已由 2 升级为 3，并在本轮升级为 4。

- 未保存温度或仍使用旧默认 `0.45` 的用户迁移到 `1`；
- 未保存最大输出或仍使用旧默认 `5200` 的用户迁移到 `10000`；
- 版本 4 新增 `requestTimeoutMs`；旧设置自动取得 `90000` 毫秒默认值，不需要重新保存；
- 超时值保存时统一限制在 `30000—900000` 毫秒，界面以秒显示；
- 用户明确保存的其他数值保持不变；
- 已有聊天档案在读取时补充空的平行世界历史，不要求手工清档。
- 已有角色的 `knowledge` 在读取时迁移为来源标记为 `legacy / 既有档案` 的 `known` 账目；
- 已有 `doesNotKnow` 原样保留为硬盲区；
- 旧聊天没有秘密登记簿时自动补为空数组，不改变聊天级存储键，也不要求重新开档。
- 旧聊天没有 `turnFacts` 与可靠在场缓存时自动补为空结构；后续楼层开始按新协议积累，不回写或猜测旧楼层目击者。

## 12. 界面

视觉方向继续使用“明末值房案牍”：

- 宋体气质只用于品牌标题和少量印章；
- 长正文、设置、事件和档案使用清晰的无衬线中文字体；
- 总览、世事、旁线、档案和设置围绕真实数据组织；
- 推演生命周期提示显示在酒馆主界面顶部横幅，不要求用户打开天下演化面板查看；
- 运行横幅提供“取消”按钮；完成、失败和取消使用不同颜色与文案，移动端按钮保持可触控尺寸；
- 档案页“信息盲区”汇总无人目击事实、可发现痕迹、隐藏秘密、人物明确未知、人物怀疑/误信、在途情报和未证消息，不再只显示本轮压缩包；
- 旁线页面突出最新两段场景，并允许回看最近回合；
- 不在聊天正文中展示或折叠平行世界。

移动端要求：

- iframe 使用动态视口单位并考虑安全区；
- 顶栏只保留品牌和关闭按钮；
- 主内容单列滚动；
- 底部操作区固定为四个栏目加设置、重新推演；
- 设置抽屉在小屏变为全屏页面；
- 最终移动端媒体查询必须位于桌面覆盖之后，避免被后续规则反向覆盖；
- 不出现横向滚动；
- 触控按钮最小高度 40px。
